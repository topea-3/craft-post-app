# 印刷・レイアウトの実現方式の検討・決定（TOP-10）

年賀状をはじめとする各種はがきの宛名印刷およびレイアウトをどのように実現するかの候補比較と採用方針をまとめたドキュメントです。

※ デスクトップは **Tauri**（TOP-7）、フロントは **React + TypeScript**（TOP-8）、永続化は **SQLite**（TOP-9）が確定しているため、印刷・レイアウトはこれらと整合する形で検討する。

---

## 1. 検討の範囲と観点


| 観点            | 内容                                        |
| ------------- | ----------------------------------------- |
| **印刷対象**      | はがきサイズ、縦書き／横書き、宛名面・デザイン面の扱い               |
| **テンプレートの管理** | テンプレートファイル、DB、コード内定義のいずれで持つか              |
| **レイアウトエンジン** | HTML+CSS→PDF、専用ライブラリ、OS ネイティブ API などの候補比較 |
| **印刷プレビュー**   | 有無と実装方法（画面内プレビュー、印刷ダイアログなど）               |


---

## 2. 印刷対象の前提（はがき仕様）

### 2.1 官製はがきのサイズと印刷可能範囲


| 項目         | 値                     | 備考                  |
| ---------- | --------------------- | ------------------- |
| **用紙サイズ**  | 100mm × 148mm（縦×横）    | 官製はがき標準。            |
| **余白（必須）** | 周囲 5mm                | 裁ち落としは不可。           |
| **印刷可能範囲** | 実質 94mm × 142mm（余白除く） | 切手枠・郵便番号枠は印刷しない。    |
| **文字サイズ**  | 6pt 以上推奨              | 6pt 未満はかすれ・つぶれの可能性。 |
| **解像度**    | 350〜400dpi（原寸）        | 印刷品質を考慮した目安。        |


※ 宛名面は縦書きが一般的。横書きも選択可能にするとよい。

### 2.2 本アプリで想定する印刷物

- **宛名面**: 住所・氏名・敬称などをはがきサイズに合わせてレイアウト。縦書き／横書きの切り替えを想定。
- **デザイン面（任意）**: 年賀状などでイラスト・文面を配置する場合は、同じ用紙サイズでレイアウト可能にすることが望ましい（将来拡張）。

## 3. レイアウトエンジンの候補比較

### 3.1 候補一覧


| 候補                          | 概要                                                                                                                                          |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **HTML+CSS → PDF（フロントで生成）** | ブラウザ/WebView 上で HTML をレンダリングし、html2canvas+jsPDF や html2pdf.js で PDF 化。または @react-pdf/renderer で React コンポーネントから直接 PDF を生成。                  |
| **専用 PDF ライブラリ（Rust 側）**    | Rust の PDF 生成クレート（例: printpdf, genpdf）で Tauri バックエンドから PDF を生成。レイアウトはコードまたはテンプレートで記述。                                                       |
| **OS ネイティブ印刷 API**          | Windows: WebView2 の PrintToPdf 等。Tauri 公式には印刷 API はなく、コミュニティプラグイン（tauri-plugin-printing-ext）や Wry の with_webview 経由で WebView2 にアクセスする必要がある。 |


### 3.2 検討観点ごとの整理

#### 3.2.1 Tauri・React スタックとの相性


| 候補                       | 相性  | 備考                                                                                                                                |
| ------------------------ | --- | --------------------------------------------------------------------------------------------------------------------------------- |
| **HTML+CSS → PDF（フロント）** | ◎   | 既存の React コンポーネント・CSS を流用できる。はがきサイズ（100×148mm）は @react-pdf/renderer の Page size でカスタム指定可能（pt 換算で指定）。html2canvas+jsPDF もカスタムサイズ対応。 |
| **Rust 専用 PDF ライブラリ**    | △   | レイアウトを Rust 側で記述する必要があり、UI（React）とレイアウト定義が二重になる。縦書き・フォントの細かい制御は手間がかかる。                                                            |
| **OS ネイティブ印刷**           | △   | Tauri 標準では未サポート。Windows は WebView2 経由で PrintToPdf を叩く実装が可能だが、プラットフォーム別の実装・メンテ負荷が大きい。                                              |


#### 3.2.2 はがきレイアウト（余白・フォント・縦書き）のしやすさ


| 候補                      | レイアウトのしやすさ | 備考                                                                                              |
| ----------------------- | ---------- | ----------------------------------------------------------------------------------------------- |
| **@react-pdf/renderer** | ◎          | Page の size を [幅, 高さ]（pt）で指定可能。余白・フォントサイズ・配置を React コンポーネントで宣言的に書ける。縦書きはコンポーネントの回転やテキスト方向で対応可能。 |
| **html2canvas + jsPDF** | ○          | 既存 HTML をそのままキャプチャして PDF 化。はがき用の HTML を 100×148mm で用意すればよい。縦書きは CSS writing-mode 等で対応。          |
| **Rust PDF クレート**       | △          | 座標・フォントを自分で管理する必要があり、縦書きや複雑なレイアウトは実装コストが高い。                                                     |


#### 3.2.3 保守性・エコシステム


| 候補                      | 保守性  | 備考                                                                        |
| ----------------------- | ---- | ------------------------------------------------------------------------- |
| **@react-pdf/renderer** | 高い   | React エコシステム内で完結。型・コンポーネントの再利用がしやすい。カスタムページサイズは pt 換算（1mm ≒ 2.8346pt）で指定。 |
| **html2canvas + jsPDF** | 高い   | 導入コストが低く、既存の React 画面をそのまま PDF 化する用途に強い。                                  |
| **OS ネイティブ / Rust PDF** | やや低い | プラットフォーム依存や Rust 側のレイアウトロジックが増える。                                         |

## 4. テンプレートの管理方法


| 方式             | 内容                                               | メリット                   | デメリット                |
| -------------- | ------------------------------------------------ | ---------------------- | -------------------- |
| **コード内定義**     | 宛名レイアウトを React コンポーネントや定数（余白・フォントサイズ等）としてコードに持つ。 | 実装が単純。バージョン管理しやすい。     | レイアウト変更のたびにコード変更が必要。 |
| **DB（SQLite）** | テンプレート名・余白・フォント設定などをテーブルで保持。                     | ユーザーが後からテンプレートを増やしやすい。 | スキーマ設計・編集 UI が必要。    |
| **テンプレートファイル** | JSON/YAML 等のファイルでレイアウト仕様を定義し、アプリが読み込む。           | コードと分離でき、非開発者でも編集しうる。  | ファイル配置・読み込み処理が必要。    |


**方針**: まずは **コード内定義**（React コンポーネント + 設定定数）で「標準の宛名レイアウト」を 1 つ用意する。余白・フォントサイズ・縦書き/横書きなどの**基本レイアウト仕様はコード内の定数または設定オブジェクト**で持つ。将来、複数テンプレートやユーザー編集が必要になった段階で、SQLite にテンプレート設定を移すか、ファイル読み込みを検討する。

## 5. 印刷プレビューの有無・実装方法


| 方式                | 内容                                                                                                                                 |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **画面内プレビュー**      | 印刷用レイアウトをそのまま React で描画し、画面上で「印刷イメージ」として表示する。PDF エンジンが @react-pdf/renderer の場合、同一コンポーネントをプレビュー用にレンダリングする方法もある（react-pdf のプレビュー表示）。 |
| **印刷ダイアログ**       | ブラウザの window.print() または Tauri 経由で OS の印刷ダイアログを開く。用紙サイズをはがきに合わせる設定はユーザーまたはアプリ側で行う。                                                 |
| **PDF 出力後のプレビュー** | いったん PDF を生成し、別ウィンドウまたはアプリ内ビューアで開く。Tauri ではファイル保存後に OS の既定アプリで開く、または WebView で PDF 表示するなどの方法がある。                                   |


**方針**: **画面内プレビューを用意する**。印刷前に宛名・余白・フォントを確認できるようにする。実装は「印刷用レイアウトと同じデータ・同じコンポーネント（または同じレイアウト仕様）を画面に表示する」形とし、PDF 生成はプレビュー確認後に実行する。印刷実行は、(1) PDF を生成してユーザーが保存・印刷する、(2) または OS 印刷ダイアログを呼ぶ、のいずれかまたは両方を検討する（詳細は実装タスクで決定）。

## 6. 基本的なレイアウト仕様（方針のメモ）

採用方針に合わせ、以下の仕様をコード内（定数・型）で定義することを推奨する。


| 項目          | 方針                                                      |
| ----------- | ------------------------------------------------------- |
| **用紙**      | 官製はがき 100mm × 148mm。                                    |
| **余白**      | 周囲 5mm（印刷可能範囲 94mm × 142mm）。                            |
| **フォント**    | 日本語対応フォント（OS に同梱の明朝・ゴシック等を利用。具体的なフォント名は実装時に指定）。         |
| **文字サイズ**   | 宛名・住所などは 6pt 以上。見出しや敬称は 7〜10pt 程度を想定（要調整）。              |
| **縦書き／横書き** | 宛名面は縦書きをデフォルトとし、横書きオプションを用意する。                          |
| **単位**      | @react-pdf/renderer 利用時は pt（1mm ≒ 2.8346pt）で統一すると扱いやすい。 |


※ 上記は「方針」レベル。実際の数値（行間・字間・フォントファミリー）は実装時に調整する。

## 7. 採用の決定

### 決定: **フロントエンドで HTML/React ベースのレイアウトと PDF 生成を行う**

- **レイアウト・PDF 生成**: **@react-pdf/renderer** を第一候補とする。はがきサイズ（100×148mm → pt 換算で約 283×420pt）の Page を定義し、宛名・住所・敬称などを React コンポーネントで配置する。縦書きはライブラリのサポート範囲で実装する（不足があれば html2canvas+jsPDF の併用やレイアウトの工夫を検討する）。
- **テンプレート**: 初期は**コード内定義**（レイアウト用 React コンポーネント + 余白・フォント等の定数）。必要に応じて後から SQLite や設定ファイルに移す。
- **プレビュー**: **画面内プレビュー**を実装する。印刷用レイアウトと同一のデータ・仕様で画面に表示し、確認後に PDF 生成または印刷ダイアログを呼ぶ。

### 理由（簡潔なメモ）

1. **スタックとの一貫性**: 既に React + TypeScript が採用されているため、レイアウトも React 内で完結させると保守しやすい。Tauri 標準の印刷 API はないため、フロントで PDF を生成する方式が現実的。
2. **はがきレイアウト**: @react-pdf/renderer はカスタムページサイズ・余白・フォントを宣言的に指定でき、官製はがきの仕様（100×148mm、5mm 余白）に合わせやすい。
3. **Rust 側 PDF を採用しない理由**: レイアウトを Rust で再実装する必要があり、縦書き・フォントの制御が重い。UI は React で統一した方が一貫性がある。
4. **OS ネイティブ印刷を主軸にしない理由**: Tauri 公式でサポートされておらず、プラットフォーム別の実装コストが高い。まずは PDF を生成し「保存または印刷」で対応する方が汎用的。

## 8. 次のアクション

- プロジェクトに **@react-pdf/renderer** を導入し、はがきサイズ（100×148mm）の Page と宛名用のサンプルレイアウトを 1 つ実装する。
- 上記「6. 基本的なレイアウト仕様」を、定数・型としてコード内に定義する（例: `layoutSpec.ts` やコンポーネント内の定数）。
- 印刷プレビュー用の画面（同一レイアウトを画面に表示）を React で用意する。
- 要件・制約ドキュメントに「印刷・レイアウト方式: フロント（@react-pdf/renderer）+ コード内テンプレート（TOP-10 で決定）」を追記する。
