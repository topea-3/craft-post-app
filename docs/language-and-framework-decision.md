# 使用言語・フレームワークの決定（TOP-8）

Craft Post App の実装に用いるプログラミング言語・UI フレームワークの候補比較と採用決定をまとめたドキュメントです。

※ デスクトップシェルは TOP-7 で **Tauri** 採用済みのため、本タスクでは **フロントエンド（WebView 上で動く UI）の言語・フレームワーク** を対象とする。Tauri のバックエンドは **Rust** で固定となる。

---

## 1. 前提と候補の範囲

- **バックエンド（Tauri シェル）**: Rust（Tauri に含まれる。ネイティブ機能・ストレージ連携などは必要に応じて Rust で拡張）。
- **フロントエンド**: Web 技術（HTML/CSS/JS または TS）で実装。ここで「言語」と「UI フレームワーク」を決定する。

### 検討対象

| 候補 | 概要 |
|------|------|
| **TypeScript + React** | 型付き JS + コンポーネント志向の UI ライブラリ。エコシステムが非常に大きい。 |
| **TypeScript + Vue** | 型付き JS + 渐进的なフレームワーク。SFC と Composition API が中心。 |
| **TypeScript + Svelte** | 型付き JS + コンパイル時に DOM を生成するフレームワーク。ランタイムが軽い。 |
| **TypeScript のみ（Vanilla）** | フレームワークなし。DOM 操作や軽量ライブラリで UI を構築。 |

---

## 2. 検討観点ごとの整理

### 2.1 スキルセット・学習コスト

| 候補 | 学習コストの目安 | 備考 |
|------|------------------|------|
| **TypeScript + React** | 中。React の概念（Hooks, 状態管理）を押さえればよい。 | 情報量が多く、入門〜中級の記事・書籍が豊富。 |
| **TypeScript + Vue** | 中。テンプレートと Composition API に慣れればよい。 | 公式ドキュメントが丁寧で、日本語も充実。 |
| **TypeScript + Svelte** | 低〜中。HTML に近い書き方で、Vue よりシンプルな印象。 | エコシステムは React/Vue より小さい。 |
| **TypeScript のみ** | 低（フレームワーク分）。ただし大規模 UI では設計が重くなる。 | 小規模なら速いが、コンポーネント化・状態管理は自前で設計が必要。 |

**メモ**: Web 開発経験があり TypeScript を使える前提なら、React / Vue / Svelte いずれも「追加の学習コスト」は許容範囲。既に React や Vue を使っている場合はそのまま流用しやすい。

---

### 2.2 エコシステム・ライブラリ事情

| 候補 | エコシステム | 備考 |
|------|--------------|------|
| **TypeScript + React** | 非常に充実。npm の UI 系パッケージの多くが React 対応または React 優先。 | フォーム・テーブル・日付・ローカルストレージ連携など選択肢が最多。 |
| **TypeScript + Vue** | 充実。Vue 3 + Vite の組み合わせが標準的。 | 公式ルーター・状態管理（Pinia）が揃っており一貫した開発がしやすい。 |
| **TypeScript + Svelte** | 成長中。SvelteKit でフルスタックも可能（本アプリでは Tauri がバックエンドのため Svelte 単体で十分）。 | コンポーネント数は React/Vue より少ないが、Tauri と組み合わせた事例は増えつつある。 |
| **TypeScript のみ** | フレームワークに依存しないライブラリはすべて利用可能。 | UI パーツは自前または軽量ライブラリ（例: Lit）の選択が必要。 |

**要件との対応**: オフライン・ローカル保存・エクスポート/インポート・バックアップ検討はいずれの組み合わせでも実現可能。React は「Tauri + React」の公式テンプレートや記事が多く、初期構築の参考にしやすい。

---

### 2.3 将来の保守性・拡張性

| 候補 | 保守性・拡張性 | 備考 |
|------|----------------|------|
| **TypeScript + React** | 高い。コンポーネント分割・型による保守性が取りやすい。大規模化してもパターンが確立している。 | 採用企業が多く、人を迎え入れやすい。 |
| **TypeScript + Vue** | 高い。SFC でテンプレート・ロジック・スタイルが一ファイルにまとまり、コンポーネント単位の保守がしやすい。 | 日本でも利用が多く、情報が得やすい。 |
| **TypeScript + Svelte** | 中〜高。バンドルが小さく、長期運用時の依存も少なめ。 | コミュニティは React/Vue より小さいが、プロジェクト規模が個人〜小規模なら十分。 |
| **TypeScript のみ** | 設計次第。コンポーネント境界を自前で決める必要があり、規模が大きくなると設計負荷が増す。 | 小規模・シンプルな UI なら軽量で長く持たせやすい。 |

**メモ**: 個人〜小規模チーム・1 端末 1 ユーザーという前提では、React / Vue / Svelte のいずれも「保守性・拡張性」は要件を満たす。差は「情報量・採用実績」で、React が最も有利。

---

## 3. Tauri との相性

| 候補 | Tauri との相性 | 備考 |
|------|----------------|------|
| **TypeScript + React** | ◎ 公式テンプレートあり。`create-tauri-app` で React + TS を選べる。 | ドキュメント・サンプルが多く、初回セットアップが最短。 |
| **TypeScript + Vue** | ○ 公式で Vue テンプレートが提供されている。 | 問題なく Tauri と組み合わせ可能。 |
| **TypeScript + Svelte** | ○ コミュニティ含め Svelte + Tauri の組み合わせは増えている。 | 公式テンプレートも選択可能。 |
| **TypeScript のみ** | ○ Tauri は任意の Web フロントを載せられる。 | ビルド設定（Vite 等）を自前で用意する必要あり。 |

---

## 4. 採用の決定

### 決定: **TypeScript + React** を採用する

### 理由（簡潔なメモ）

1. **TOP-7 との一貫性**: デスクトップは Tauri（Rust）で確定。フロントは Web 技術のため、型安全と保守性のために **TypeScript** を採用。UI はコンポーネント化しやすい **React** を採用する。
2. **エコシステム**: フォーム・テーブル・日付ピッカー・ローカルストレージ連携など、要件（データ入力・エクスポート/インポート・バックアップ検討）に必要なライブラリが React 向けに最も豊富。
3. **Tauri との組み合わせ**: `create-tauri-app` で React + TypeScript を選べ、公式ドキュメント・サンプルが多く、初期構築と今後の参照がしやすい。
4. **保守性・拡張性**: コンポーネント分割と型による保守性が取りやすく、個人〜小規模チーム規模でも長く保守しやすい。情報量と採用実績が多く、将来メンバーが増えた場合も共有しやすい。
5. **他候補を選ばない理由**  
   - **Vue**: 問題なく使えるが、Tauri 公式の「最初の一歩」が React であることが多く、同じ Web 技術なら React で揃えた方がドキュメント参照が楽。  
   - **Svelte**: 軽量で良いが、本アプリでは「オフライン・ローカル主体」でバンドルサイズは Tauri 側で既に小さいため、Svelte のメリットがやや相対的に小さい。エコシステムの豊富さでは React が有利。  
   - **Vanilla TS**: 小規模なら可能だが、画面・コンポーネントが増えると設計負荷が高くなる。最初から React でコンポーネント境界を明確にした方が拡張しやすい。

---

## 5. 次のアクション

- Tauri プロジェクトを **React + TypeScript** で初期化する（例: `create-tauri-app` で React + TS を選択）。
- アーキテクチャ設計タスクで、フロント（React コンポーネント構成・状態管理方針）と Tauri 側（Rust コマンド・ストレージ連携）の責務分担を具体化する。
- 要件・制約ドキュメントに「使用言語: TypeScript（フロント）, Rust（Tauri シェル）」「UI フレームワーク: React」を追記するか検討する。
