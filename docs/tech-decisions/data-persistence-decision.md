# データ永続化方式の検討・決定（TOP-9）

Craft Post App において、住所情報やはがき送受信履歴などをどのように永続化するかの候補比較と採用方針をまとめたドキュメントです。

※ バックエンドは TOP-7 で **Tauri（Rust）**、フロントは TOP-8 で **React + TypeScript** が確定しているため、永続化は **Tauri シェル（Rust）側** で保持し、フロントは Tauri のコマンド／API 経由でアクセスする前提とする。

---

## 1. 候補技術

| 候補 | 概要 |
|------|------|
| **SQLite** | ファイル 1 つで完結するリレーショナル DB。Rust では `rusqlite` や `sqlx`で利用。ACID 保証・SQL による問い合わせが可能。 |
| **tauri-plugin-store** | Tauri 公式のキーバリュー型ストア。設定や少量のキー単位データ向け。 |
| **Realm** | オブジェクトストア型 DB。モバイル（Swift/ Kotlin）での採用が多く、Rust からの利用は事例が少ない。 |
| **LiteDB** | .NET 系の組み込み DB。C# ネイティブであり、本プロジェクトの Rust バックエンドとは相性が悪い。 |

**本タスクで主に検討する候補**: **SQLite** と **tauri-plugin-store**。Realm / LiteDB は技術スタック（Rust 中心）との相性から今回は候補外とする。

---

## 2. 検討観点ごとの整理

### 2.1 ローカル DB の選定

| 候補 | データモデル | Rust との相性 | 備考 |
|------|--------------|---------------|------|
| **SQLite** | リレーショナル（テーブル・リレーション）。住所録・履歴の「複数エンティティと関係」を自然に表現できる。 | ◎ `rusqlite` / `sqlx` が成熟。スキーマのマイグレーション（例: sqlx-cli）も利用可能。 | 1 ファイル = 1 DB のため、バックアップはファイルコピーで完結。エクスポート時に JSON/CSV を生成する実装も容易。 |
| **tauri-plugin-store** | キーバリュー。複雑なリレーションや検索条件はアプリ側で組み立てる必要がある。 | ◎ Tauri 公式。Rust 側からもフロントからも利用可能。 | 設定・ユーザー設定・小さいマスタ向け。住所録や履歴のような「一覧・検索・関連」が中心のデータには不向き。 |

**要件との対応**: 住所情報・はがき送受信履歴は「エンティティが複数」「検索・フィルタ・関連付け」が必要なため、**リレーショナルな構造**が適している。この観点では **SQLite が適している**。

---

### 2.2 データスキーマの大まかな構造

主要なエンティティと関係のラフなイメージを以下に示す。

- **住所録（Address / 住所録エントリ）**  
  - 氏名、住所、連絡先、メモ、グループ（任意）など。  
  - はがき送付先・差出人として参照される。
- **はがき送受信履歴（History / 履歴）**  
  - 送付日、種別（送信/受信）、宛先・差出人（住所録への参照）、内容メモなど。  
  - 住所録の「どのエントリに紐づくか」を外部キーで持つ想定。
- **グループ（任意）**  
  - 住所録を分類するためのグループ。  
  - 住所録エントリが「1 つのグループに属する」などの関係を将来持たせられる。

**永続化の主体**: 上記は **SQLite のテーブル**として保持する。  
（設定類のみ tauri-plugin-store を併用するかはアーキテクチャ設計時に判断可能。）

---

### 2.3 バックアップ・リストアの手段

| 方式 | 内容 |
|------|------|
| **手動エクスポート** | ユーザー操作で「全データまたは選択データを JSON / CSV で保存」する機能を提供する。SQLite の内容をアプリ側で読み、要件どおり標準形式（JSON/CSV 等）で出力する。 |
| **ローカル自動バックアップ** | 詳細（頻度・保存先・保持数）は機能設計時に決める。実装案としては、(1) 定期的に SQLite ファイルを指定フォルダにコピーする、(2) または定期的に同じ形式の JSON を出力して保存する、のいずれかまたは両方を検討する。 |
| **リストア** | エクスポートした JSON/CSV を読み込み、SQLite に書き戻す（インポート）機能を想定する。 |

**採用方針**: 永続化を **SQLite 1 ファイル** にまとめることで、  
- バックアップ = そのファイルのコピー、またはアプリが生成する JSON/CSV  
- リストア = ファイル差し替え、または JSON/CSV のインポート  
のいずれも実現しやすい。要件の「手動エクスポート」「ローカル自動バックアップ」「リストア」を満たす。

---

### 2.4 クラウド同期の有無・将来的な追加余地

| 観点 | 方針 |
|------|------|
| **現時点** | 要件どおり **クラウド同期は用意しない**。データは端末ローカルの SQLite のみに保存する。 |
| **将来の追加余地** | スキーマ設計時に、必要なら「同期用 ID」「更新日時」などのカラムをラフに想定しておく。実際のクラウド連携は別タスクで検討する。 |

---

## 3. 採用の決定

### 決定: **SQLite** をローカル永続化の主軸とする

- **実装**: Rust 側で **rusqlite** または **sqlx** のいずれかで SQLite にアクセスする。マイグレーションや型安全を重視する場合は sqlx を検討する。
- **データの置き場所**: Tauri のアプリデータディレクトリ（例: `app_data_dir`）配下に SQLite ファイル（例: `craft_post.db`）を 1 つ配置する想定。
- **設定など**  
  - アプリ設定・ユーザー設定など、キー単位の小さいデータは **tauri-plugin-store** の併用を検討してよい（アーキテクチャ設計時に判断）。

### 理由（簡潔なメモ）

1. **データの性質**: 住所録・送受信履歴はエンティティとリレーションが明確なため、リレーショナルな SQLite が適している。
2. **Tauri/Rust との相性**: Rust の SQLite クレート（rusqlite / sqlx）が成熟しており、Tauri のネイティブ層でそのまま利用できる。
3. **バックアップ・リストア**: 1 ファイル DB のためコピーによるバックアップが容易。要件の「JSON/CSV 等でのエクスポート」も、DB 内容を読み出して出力する形で実現できる。
4. **将来の拡張**: クラウド同期を後から追加する場合も、スキーマにカラムを足すなどで対応可能。
5. **Store を主軸にしない理由**: キーバリューは「一覧・検索・リレーション」に向かず、住所録・履歴のような構造データには不向き。設定用途に留める。

## 4. 主要エンティティと関係のラフ図（イメージ）

```
┌─────────────────────┐       ┌─────────────────────────────┐
│  Group（グループ）   │       │  Address（住所録）           │
│  - id               │───┐   │  - id                        │
│  - name             │   │   │  - group_id (FK, 任意)        │
└─────────────────────┘   └──<│  - name, postal_code, ...    │
                              │  - address, tel, memo, ...   │
                              └──────────────┬──────────────┘
                                             │
                                             │ 宛先 / 差出人
                                             ▼
                              ┌─────────────────────────────┐
                              │  History（送受信履歴）        │
                              │  - id                        │
                              │  - address_id (FK)           │
                              │  - kind (送信/受信)           │
                              │  - occurred_at, memo, ...    │
                              └─────────────────────────────┘
```

- **Address**: 住所録 1 件。任意で **Group** に属する。
- **History**: はがきの送信/受信 1 件。**Address** を宛先または差出人として参照する。
- 上記はあくまでラフなイメージ。カラム名・正規化の程度は詳細設計で確定する。
