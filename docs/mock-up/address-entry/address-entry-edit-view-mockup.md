## AddressEntry 編集画面モック（v1）

- **画面ID**: `ADDR003`
- **画面名**: 住所録編集

---

### 1. 画面レイアウト（フォーム）

- **上部エリア**
  - 左上: 画面タイトル「住所録編集」
  - タイトル直下に対象の現在表示名をサブタイトル表示:
    - 例: `山田 太郎・花子`
  - 右上: 「アーカイブ」メニュー／「戻る」リンク

- **フォーム本体**
  - レイアウト・項目構成は作成画面（`ADDR002`）と共通。
  - 初期値として既存の `AddressEntry` の値を反映。

#### 1.1 宛先情報・住所情報・メモ

- 項目一覧は作成画面モックを参照。  
  差分として以下を想定:

- **連名の表示順**
  - `coRecipients` を `order_index` 順（DB 上）で表示。
  - UI 上でドラッグ＆ドロップによる並び替えを行うかは将来検討（v1 では行単位での上下ボタン程度でも可）。

#### 1.2 差出人の紐づき管理（宛名側）

- **目的**
  - この `AddressEntry`（宛名）に紐づく差出人（`SenderEntry`）を `SenderAddressLink` で管理する。
  - v1 では宛名 1 件あたり、（有効データの範囲では）紐づく差出人は高々 1 人。

- **現在の紐づき状態**
  - 差出人が紐づいている場合:
    - 現在の差出人を表示（`SenderLabel.value` / `joinRecipients(primaryName, coRecipients)`）
    - 「紐づけ解除」ボタンで `SenderAddressLink` を削除
  - 紐づきがない場合:
    - 「差出人未設定」と表示

- **差出人の選択（追加/置き換え）**
  - 「差出人を選択」ボタン
    - クリック → `SenderEntry` の選択 UI を開く（`archivedAt` が未設定＝有効な差出人のみ）
  - 置き換え確認:
    - すでに別の差出人に紐づいている状態で新しい差出人を選んだ場合
    - 確認ダイアログで置き換えを促す
      - 「この宛名はすでに別の差出人に紐づいています。置き換えますか？」
    - OKの場合: 既存リンクを削除して付け替え
    - キャンセルの場合: 変更しない

---

### 2. ボタン・アクション

- **画面下部ボタンエリア**
  - 左: 「キャンセル」ボタン（セカンダリ）
    - クリック → 変更がある場合は確認ダイアログ表示。
    - 確認後 → 詳細画面（`ADDR004`）または一覧画面（`ADDR001`）へ戻る設計。
  - 中央左寄せ: 「アーカイブ」ボタン（またはメニュー）
    - クリック → 確認ダイアログ:
      - 「この住所録エントリをアーカイブしますか？一覧からは非表示になりますが、データは保持されます。」
    - 確認後 → `archivedAt` を設定してアーカイブし、一覧画面（`ADDR001`）へ遷移（`updatedAt` は変えない）。
  - 右: 「保存」ボタン（Primary）
    - クリック → バリデーション → `UpdateAddressEntry` 実行。
    - 成功後の遷移先候補:
      - A: 詳細画面（`ADDR004`）へ遷移。
      - B: 一覧画面（`ADDR001`）へ戻る。

---

### 3. バリデーションとエラー表示

- **内容**
  - 作成画面（`ADDR002`）と同一ルール。
  - 更新時も同じドメイン不変条件を通過する必要がある。

- **エラー表示**
  - フィールド単位のエラーメッセージ＋画面上部にまとめてメッセージ（例: 「入力内容に不備があります。赤字の項目を修正してください。」）。

---

### 4. 補助情報エリア（オプション）

- フォーム下部またはサイドバーに読み取り専用情報を表示してもよい:
  - 作成日時: `createdAt`
  - 最終更新日時: `updatedAt`
  - ID: `id`

---

### 5. UX メモ

- **フォーム共通化**
  - 作成・編集で同じコンポーネントを使い、モード（create/edit）でタイトルやボタンラベルだけ切り替える方針。

- **アーカイブと物理削除**
  - v1 では原則アーカイブのみを UI に出し、物理削除は管理者向けツールなど別経路を想定。
