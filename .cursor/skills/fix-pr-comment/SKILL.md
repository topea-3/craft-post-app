# PR コメント修正

PR コメントのリンクを引数で受け取り、その後以下のフローでコメントについて修正する。

## 引数

| 引数 | 必須 | 説明 |
|------|------|------|
| PR コメント URL | Yes | GitHub のレビューコメント／Issue コメント／レビューへのリンク |

対応する URL 例:

- `.../pull/N#discussion_r<id>`（インラインレビューコメント）
- `.../pull/N#issuecomment-<id>`（PR 会話コメント）
- `.../pull/N#pullrequestreview-<id>`（レビュー単位）

取得手順の詳細は [references/comment-fetch.md](references/comment-fetch.md) を読む。
返信・Resolve は [references/comment-reply-resolve.md](references/comment-reply-resolve.md) を読む。

## 構成ファイルの責務

| ファイル | 責務 |
|----------|------|
| `SKILL.md`（本ファイル） | 起動条件、自律実行ワークフロー、不変ルール |
| `references/comment-fetch.md` | URL 解析と `gh` によるコメント／スレッド取得 |
| `references/comment-reply-resolve.md` | Push 後の返信投稿とスレッド Resolve |

## 不変ルール

- 引数の URL が無い・パースできない場合は修正に入らず、正しいリンクを求める
- 対象コメントと**紐づくスレッド**（親・返信）を揃えてから方針を立てる
- コメント範囲外のリファクタや無関係な変更はしない
- 判断や確認が必要なときは**選択肢付き**でユーザーに指示を仰ぎ、推測で進めない
- コミット／プッシュは Step 5 の出口条件を満たしたときだけ行う（ユーザーがこのスキルで依頼している場合はコミット許可とみなす）
- **Push 成功後は、今回対応した該当コメントへ返信し、解決可能なスレッドは Resolve する**（Step 6。ユーザーがこのスキルで依頼している場合は返信・Resolve 許可とみなす）
- このリポジトリでは PR base は原則 `develop`（本スキルはコメント修正が主目的。新規 PR 作成時は `develop` 向け）

## 自律実行ワークフロー

以下を上から順に実行する。Task Progress は作業メモに複製し、進むごとに更新する。

Step 3–5 はレビューで再修正が必要なら繰り返す（最大 3 周）。収束しない場合は未達項目と選択肢をユーザーに確認して停止する。

```
Task Progress:
- [ ] Step 1: PRコメントとそれに紐づくコメントを取得する
- [ ] Step 2: コメント内容を確認して対応方針を計画する
- [ ] Step 3: 方針に沿って修正する
- [ ] Step 4: 修正内容をレビューする
- [ ] Step 5: 再修正またはコミットとプッシュ
- [ ] Step 6: 該当コメントへ返信し Resolve する
```

### Step 1: PRコメントとそれに紐づくコメントを取得する

1. 引数の URL をパースする（[references/comment-fetch.md](references/comment-fetch.md)）
2. 対象コメント本文・作者・パス／行・作成時刻を取得する
3. 同一スレッドの親・返信をすべて取得する
4. 必要なら該当ファイルの現行コードを読む（コメント引用差分ではなく現コードを正とする）

### Step 2: コメント内容を確認して対応方針を計画する。このとき判断や確認が必要な内容は選択肢を提示して指示を仰ぐ

1. 指摘の意図・必須度・影響範囲を整理する
2. 対応案（修正する／しない／別案）を短くまとめる
3. **判断や確認が必要な内容は選択肢を提示して指示を仰ぐ**。曖昧なまま Step 3 に進まない
4. ユーザー承認後の方針を作業メモに残す

### Step 3: 方針に沿って修正する

1. 方針どおり最小差分でコード／テスト／ドキュメントを直す
2. 関連する既存テストや検証コマンドがあれば実行する
3. Step 6 用に、対応した各コメントへの短い返信文案を用意する（投稿自体は Step 6）

### Step 4: 修正内容をレビューする

差分と方針を照合し、少なくとも次を確認する。

- コメントの指摘が解消されているか
- 方針外の変更が混ざっていないか
- 明らかな回帰・漏れがないか

結果を「ブロッカー / should / nit・任意」に分けて記録する。

### Step 5: レビュー結果でshould以上の指摘、または明らかに直したほうが良い指摘があれば修正方針を立てて3から繰り返し、無ければ、コミットとプッシュを行う

1. **should 以上**の指摘、または**明らかに直したほうが良い**指摘がある → 修正方針を立てて **Step 3 から繰り返す**
2. 無い → 変更をステージし、簡潔なコミットメッセージでコミットし、リモートへプッシュする
3. Push 成功後は **Step 6 へ進む**（コード変更が無く Push しない場合でも、既に remote に反映済みでコメント対応だけ残っているなら Step 6 を行う）

コミット時はリポジトリの git 安全ルール（hooks スキップ禁止、秘密情報を含めない等）に従う。

### Step 6: 該当コメントへ返信し Resolve する

Push 後（または修正が既に remote にあるとき）、[references/comment-reply-resolve.md](references/comment-reply-resolve.md) に従う。

1. **今回対応した該当コメント**だけを対象にする（無関係な未解決スレッドは触らない）
2. 各対象について、何をどう直したか／対応しない場合はその理由を短く返信する（コミット SHA があれば含める）
3. インラインレビュー／レビュー単位のスレッドは返信後に **Resolve** する
4. `issuecomment` は返信のみ（Resolve API は無い）
5. サマリを返す（対象コメント URL、方針、主な変更、コミット、返信・Resolve 結果、残課題）
